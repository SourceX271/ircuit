# Ircuit 实施计划

> 需求基线见 [需求文档.md](./需求文档.md)。本文件定义工程结构、里程碑验收标准、技术决策与风险对策。

---

## 1. 验收基线

一个 Ircuit 版本算「合格」，必须同时满足：

1. 三平台（Windows / macOS / Linux）能构建、能启动、能连接、能对话。
2. 协议层有单测，`cargo test` 与 `cargo clippy -- -D warnings` 全绿。
3. 前端 `tsc --noEmit` 与 `vitest` 全绿。
4. 关键流程纯键盘可完成。
5. 无遥测、无隐式外联；凭据不出现在明文文件中。

### M1 — 协议内核
**目标**：真的能连上 IRC 并收发消息。

**已确认决策**
- 界面做到**可用的连接表单 + 服务 buffer**：用户能亲自走完「建网络 → 连接 → 入频道 → 对话」全流程。
- 验证方式：仓库内**内置 mock IRC 服务器**做自动化回归（CAP / SASL / 重连 / 分片可控可重现），同时保留连真实网络的手动验证。
- SASL 只做 **PLAIN + EXTERNAL**；SCRAM-SHA-256 需要 HMAC/PBKDF2 与多轮协商，放到 M4 与客户端证书一起做。

**交付**
- `ircuit-proto`：消息解析/序列化、IRCv3 tag 转义、mIRC 格式码编解码、消息分片、RFC 样例单测
- `ircuit-client`：tokio + rustls 连接、DNS、连接状态机、CAP LS 协商、SASL PLAIN/EXTERNAL、PING/PONG 保活、指数退避重连、事件总线
- `ircuit-testserver`：进程内 mock IRC 服务器，供集成测试与手动联调
- 可用 UI：网络配置表单 → 连接 → 加入频道 → 收发消息，服务 buffer 展示原始流量

**验收**：集成测试对着 mock 服务器跑通注册 / 入频道 / 收发 / 重连；连上 Libera.Chat 并能真实对话；断网后自动恢复；解析层单测覆盖边界样例。

### M3 — 持久化与检索
**目标**：数据不丢、可检索。

**已确认决策（2026-02，进入 M3 前确认）**

| 决定 | 原因 / 代价 |
| --- | --- |
| **凭据：Keyring 为主，加密文件为回退** | Keyring 不可用（Linux 无 secret service 等）时退回一个加密文件，启动时输入主密码解锁。代价是多一个启动解锁步骤，且必须自己实现密钥派生——因此 KDF 用成熟的 Argon2id、加密用 AEAD（XChaCha20-Poly1305 / AES-256-GCM），**绝不自己发明加密**；不做「机器派生密钥自动解锁」是因为那等于混淆而不是加密。 |
| **搜索：跳回原 buffer 并定位命中行** | 保持「一个会话一条时间线」的模型，上下文天然完整。结果面板只做索引，不做第二套会话语义。 |
| **历史：默认不限制，提供手动清理与按网络清空** | 符合 IRC 用户对「日志不该自己消失」的预期，也让「10 万条搜索 <100ms」这条验收有稳定的测试数据。自动清理留作可选项，不做默认。 |

**echo 去重：结构上解决，不做指纹匹配（已在进 M3 前实现）**

原计划写的是「echo-message 去重」，暗示要按内容+时间窗匹配自己的消息与服务器回显。实施时发现
有一条更简单也更可靠的路：**客户端本来就知道 `echo-message` 是否协商成功**，于是二选一即可——

- 协商成功：服务器会回显，客户端什么都不做，以服务器的回显为唯一事实来源；
- 协商失败：客户端把刚发出的行**本地回显**（新增 `NetworkEvent::LocalEcho`）。

任一时刻只有一条路径是活的，因此**根本没有重复需要去重**。本地回显由「把即将发出的行解析回来、
换成我们自己的前缀」得到，而不是从命令重新拼装——这样长消息被拆成多行时每行都会出现，`/me` 的
CTCP 包装也原样保留，UI 才会把它渲染成动作而不是普通消息。落库沿用同一保证。

顺带修掉一个真实缺陷：此前只有服务器回显才会产生会话消息，因此**在不支持 `echo-message` 的网络上
（例如 OFTC），用户自己发的每一句话都不会显示**。mock 服务器一直无条件回显，把这个问题完全遮住了；
现在它只在真的协商了该能力时才回显。

**前置验证（已在 `crates/ircuit-storage` 落地，进 M3 前完成）**

选型与性能不再靠猜，三项都已实测：

| 问题 | 结论 |
| --- | --- |
| 带 FTS5 的 SQLite 能否在本环境编出来 | 能。`rusqlite 0.40` + `bundled`，FTS5 已编入并有测试守着（少了它，M3 的每次搜索都会在运行时报 `no such module: fts5`，症状看起来像 SQL 写错） |
| 「10 万条 <100ms」是否成立 | 成立且余量巨大。**按真实 schema 实测**：10 万条搜索 20 次，最慢 **23.6µs**；中文短语查询在 5 万条上最慢 **255.6µs**——比预算低 2~3 个数量级 |
| 「历史不限制」的磁盘代价 | **10 万条 23.2 MiB**（含 FTS 索引、触发器与全部二级索引）。即 100 万条约 232 MiB、1000 万条约 2.3 GiB。这个数字支持「默认不限制」，也让「按网络清空」有了可解释的量级 |
| 分页会不会全表扫 | 不会。`EXPLAIN QUERY PLAN` 为 `SEARCH message USING COVERING INDEX message_buffer_time`——索引顺序与「单 buffer、按时间倒序、取一页」完全一致 |
| 写入成本 | 10 万条 5.3 秒（约 53µs/条，已含触发器维护索引）。真实聊天量级下可忽略，批量导入也够快 |

> 早期探针在一张精简表上量到 13.7 MiB / 21µs，与上表不同：那是「光秃秃的 message + FTS」，
> 没有触发器、没有二级索引。上表才是这个 schema 的真实成本，以它为准。

**中文检索必须专门处理（不能想当然）**

`unicode61` 把 CJK 表意文字当作普通字母，因此**一整段中文是一个 token**：
`今天发布了新版本` 是一个词，搜 `发布` 得到 0 条。这不是 SQLite 的缺陷，而是「没有分词词典时，
『词』就是这个意思」。

解决办法（已验证、无额外依赖、无词典）：额外索引一份「每个 CJK 字符之间插空格」的文本，
普通分词器就会逐字切分，两字词变成相邻两 token 的短语查询即可命中：

```sql
-- 索引侧：'今天发布了新版本' → '今 天 发 布 了 新 版 本'
-- 查询侧：'发布' → MATCH '"发 布"'
```

`trigram` 是另一个内置候选，但它**无法匹配少于 3 个字符的查询**，而两字中文词到处都是，
所以不作为主方案。展示用的原文来自 `message` 表，索引里的空格不会出现在界面上。

实现上的两个决定：

- **`message_fts` 是 contentless（`content = ''`）**。外部内容表会把「索引用的文本」读回来做
  snippet，而中文那份是插了空格的副本——没人想在结果列表里读 `今 天 发 布`。摘要一律取自
  `message.body`，索引因此没有理由再存一份原文。
- **`body_indexed` 可空**，拉丁文本存 NULL。逐字索引对拉丁文本与原文逐字节相同，两份都存等于
  让「永久保留」的档案体积翻倍。触发器用 `COALESCE(body_indexed, body)` 定义「索引看到的文本」，
  写入与删除必须用同一个表达式——不一致会留下永远删不掉的索引条目。实测这一步省下约 19% 体积。

**交付**
- SQLite schema（网络 / 频道 / 消息 / 用户 / 设置）+ 版本化迁移
- 全量消息落库（优先 `server-time`）。**echo 去重已在进入 M3 前结构性解决**，见下
- 上滑分页按需加载、环形内存缓冲
- FTS5 全文搜索：跨 buffer、结果跳转原文
- 会话 / 草稿 / 未读状态恢复
- 日志导出（纯文本 / HTML）
- 凭据写入 OS Keyring

**M3-3 已落地：落库与分页（设计决定，后续改动必须遵守）**

| 决定 | 原因 |
| --- | --- |
| **缓冲区归属由后端计算**（`ViewMessage::buffer`），前端不再自己推导 | 历史是按缓冲区存的。私有消息在协议上发给「我」，但会话归属发送者——两边各算一次，一旦不一致，症状不是报错而是**会话永远空白**（消息被存进一个没人读的键）。这也是「界面不重新推断协议层已知事实」这条原则的延续。 |
| **`message` 表不设外键到 `network` / `channel`** | 落库因此不依赖任何前置写入顺序，也就不存在「昵称还没定、频道还没建」时丢消息的窗口。 |
| **历史 id 用字符串过 IPC** | rowid 不满足 §7 的整数约定。它对界面只是个不透明句柄，从不参与运算。 |
| **分页游标只用时间，不强求 rowid** | 刚收到的消息其插入还在途中、没有 rowid；等它就会让「上滑」在写入落盘前毫无反应。代价是同一秒内的行可能漏掉——而可以用来打破平局的 rowid 恰恰是此刻不知道的那个。 |
| **页面按「最旧在前」返回**，并带 `exhausted` | 界面是向上**前插**，所以按绘制顺序返回，调用点不必反转（两处调用点也就不会有一处漏反转）。`exhausted` 由后端多查一行得出，界面不必从「页不满」去猜。 |
| **落库失败不得影响连接** | 磁盘满、目录只读、数据库来自更新版本，都只该让存档降级，不该让对话中断。第一次失败大声记日志、后续计数抑制，避免每条消息刷一条日志。 |
| **SQLite 一律走阻塞线程池** | `rusqlite` 是同步的，直接在 Tokio 任务里调用会占住运行时工作线程。`Connection` 包在 `Arc<Mutex<_>>` 里，锁只在阻塞闭包内持有，绝不跨 `.await`。 |
| **两张表都保留原文与解析结果**（`message.body` 与 `RawTraffic.line`） | 渲染后的行无法回答「那到底是加粗，还是真的有个控制字节」。 |

**M3-3 未做**：`network` / `channel` 行尚未写入（消息表无外键，所以不影响落库；主题与连接配置的持久化在 M4/M7/U1 需要时再加）；`msgid` / `account` 暂为空（IRCv3 标签在 M7 才接上，schema 与新加的唯一索引已就位，回填不需要迁移）。

**验收**：重启恢复全部状态；10 万条消息搜索 < 100ms；配置文件中无明文密码。

## 4. 关键技术决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| IRC 协议实现 | 自研（不依赖第三方 IRC crate） | 需要 IRCv3 全量、DCC、编码、Bouncer 精细控制 |
| IPC 契约 | tauri-specta 自动生成 TS 类型 | 避免前后端类型漂移 |
| 前端持有 socket | 否 | 协议逻辑集中在 Rust，UI 可替换、可测试 |
| 插件沙箱 | QuickJS (rquickjs) | 体积小、无 IO 权限、易设资源上限 |
| 编码检测优先级 | 手动设置 > 自动检测 | 检测会误判，用户必须能覆盖 |
| 凭据存储 | OS Keyring（非 SQLite） | 系统级加密，配置文件可安全备份 |
| 消息存储 | SQLite + FTS5 | 单文件、事务安全、全文检索开箱可用 |
| 长列表 | 虚拟滚动 + 分页加载 | 内存与帧率可控 |
| 事件传输 | 增量事件 + 环形缓冲 | 长会话不膨胀 |
| IPC 整数 | 跨 IPC 只用 32 位及以下整数 | specta 拒绝导出 `u64`/`i64` 等，见第 7 节 |
| 测试进程模型 | vitest `pool: 'threads'` | 不依赖派生子进程，容器与受限环境更稳，也更快 |

## 7. IPC 整数约定

Rust 与前端之间传整数时，**只用 32 位及以下类型**（`u8` / `i8` / `u16` / `i16` / `u32` / `i32`）。

原因：生成的 TypeScript 里整数是 JS 的 `number`（IEEE-754 双精度），只能无损表示到 2^53。
因此 `specta` 会**直接拒绝导出** `u64`、`i64`、`usize`、`isize`、`u128`、`i128`，
在编译期就报错，而不是等到线上出现精度问题。

确实需要 64 位语义时，按以下优先级处理：

1. **换更小的单位（首选）**。例如运行时长用秒而不是毫秒 —— `u32` 秒可以表示 136 年。
2. **需要绝对无损的大整数**（例如消息 ID）时用 `String` 传递，配合
   `#[specta(type = String)]` 与 serde。
3. **万不得已**才用 `#[specta(type = specta_typescript::Number)]` 显式放弃精度保护，
   并且**必须**在注释里写清为什么在这里是安全的。

## 8. 受限环境开发说明

本项目在文件与进程受限的环境（容器、CI 沙箱、受管终端）里同样可以开发，
依赖三处本机配置，均不入库。

| 问题 | 现象 | 对策 |
| --- | --- | --- |
| 缓存目录不可写 | cargo / npm 无法写 `~/.cargo`、`%LOCALAPPDATA%` | 缓存重定向到项目内 `.cache/`：cargo 用 `CARGO_HOME`，npm 用项目 `.npmrc` |
| cargo TLS 握手失败 | `schannel: AcquireCredentialsHandle failed` | `scripts/dev/cargo-proxy.mjs` 提供本机明文 HTTP registry，TLS 交给 Node |
| 禁止带管道的子进程 | Vite 探测 `net use` 时 `spawn EPERM`，vitest 起 worker 失败 | `scripts/dev/sandbox-shim.mjs` 预加载垫片；vitest 使用线程池 |
| 界面无法目视验证 | 窗口被遮挡时普通截屏只能拿到桌面像素 | `scripts/dev/capture-window.ps1` 用 PrintWindow 直接渲染窗口内容 |
| **禁止命名管道 → 任何 Chromium 界面都起不来** | 见下节 | 无对策：本环境下必须由人在沙箱外做目视验收 |

注意：`scripts/dev/*.ps1` 必须保持 **ASCII-only**。Windows PowerShell 会把无 BOM 的脚本
按 ANSI 解码，中文会破坏解析。

具体命令见 README 的「受限环境」一节。

### Chromium 在本环境无法启动（受限沙箱下已证实；权限放开后恢复正常）

> **后续更新**：本会话后期的文件沙箱放宽为 `danger-full-access` 之后，窗口与无头浏览器都能
> 正常启动，M2 的目视验收因此得以实际执行（见 §9「M2 验收 · 目视验收」）。下面记录的是
> **受限沙箱下**的结论，仍然适用于 CI / 容器等受限环境——在这些环境里不要把「跑起来看一眼」
> 当作可依赖的验证手段。

Tauri 窗口（WebView2）与无头 Edge **都不能**在受限沙箱内启动，因为 Chromium 的进程间通信
（Mojo）在 Windows 上走**命名管道**，而沙箱禁止命名管道。这不是可以提权绕过的策略问题，
是环境的硬限制。

实测记录：

| 尝试 | 结果 |
| --- | --- |
| `pnpm tauri dev`（直接运行） | vite 启动正常；`cargo` 因缺 `CARGO_HOME` 去连真实 registry 而失败 |
| 补上 `CARGO_HOME` 与 sandbox shim | **后端完全正常**：`autoconnecting spec=127.0.0.1:6667:ircuit:plain` → `registered nick=ircuit`，窗口句柄也创建了；但 `failed to create webview: WebView2 error: WindowsError(0x800700AA) 请求的资源在使用中` |
| 用 `WEBVIEW2_USER_DATA_FOLDER` 指向 `.cache/webview2` 避开残留进程的数据目录争用 | 错误变成 `0x8000FFFF 灾难性故障`——说明争用是一层原因，但不是根因 |
| 无头 Edge 截图 Vite 开发服务器 | `FATAL:mojo\public\cpp\platform\platform_channel.cc:183] Check failed: 拒绝访问 (0x5)`；伴随网络沙箱无法获取 `Dictionaries` / `Network` 目录权限 |

结论：**界面验收只能由人在沙箱外执行**，清单见 `docs/人工验收.md`。自动化测试仍然全绿，
但「测试通过」不等于「看起来对」——像素级问题（间距、对比度、拥挤）必须人眼看。

副作用（对真实用户也有用）：若上一次 `pnpm tauri dev` 留下的 WebView2 进程仍持有用户数据
目录，下一次启动会以 `0x800700AA 请求的资源在使用中` 失败、窗口不出现。处理办法是先结束残留的
`ircuit.exe`，或给这次运行换一个数据目录：

```powershell
$env:WEBVIEW2_USER_DATA_FOLDER = "$PWD\.cache\webview2"
```

## 9. 落地记录

跨里程碑的设计决定，后续改动必须遵守。

### M0–M1

| 决定 | 原因 |
| --- | --- |
| **事件回放按 `seq` 交错应用** | Tauri 事件不做缓冲，挂载前发出的事件不会重放。后端为每个网络保留有界回放（消息 500 条、原始流量 1000 条），每条事件带单调递增 `seq`；前端先订阅、再取回放，靠 `seq` 去重。回放**必须把两类事件按 `seq` 合并排序后统一应用** —— 它们共用一个计数器，先应用其中一类会把高水位推过另一类，导致整类事件被静默丢弃。 |
| **IPC 绑定只由专用 bin 生成** | `run()` 曾在 debug 下顺带导出绑定，于是运行一个陈旧的二进制会把新绑定覆盖回旧版本；前端随后调用不存在的命令而整棵树崩溃，症状（窗口全白）与原因毫无关联。现在只有 `pnpm cargo:bindings` 会写这个文件。 |
| **TLS 提供者用 ring，不用 aws-lc-rs** | 后者在 Windows 上需要额外安装 NASM 才能编译汇编优化，等于给三平台构建多加一个工具链依赖。 |
| **`ircuit-testserver` 用字符串匹配，不复用 `ircuit-proto`** | 与被测代码共享解析器，就无法发现解析器自身的缺陷。mock 必须是一个独立的见证者。 |
| **原始行输出剥离 CR/LF** | 参数里的换行能让对端（或插件）注入新命令，这是 IRC 客户端的经典漏洞；协议没有转义机制，只能剥离。 |
| **昵称字符集按 RFC 1459** | `[ ] \ ^ { } \|` 与反引号都是合法昵称字符，因此 `[me]` 是一个整体 token，不被视为提及。 |

### M2

| 决定 | 原因 |
| --- | --- |
| **命令表是唯一事实来源** | 命令的元数据（名称、别名、用法、说明）与解析行为写在同一个 `COMMANDS` 表里：解析器、Tab 补全候选与 `/help` 都从它派生。分成「一个 switch + 一段手写帮助字符串」的话，加命令的人必然只改其中一处。 |
| **命令补全候选里主名排在别名前** | 否则 `/qu` 会先补成 `/query`（`/msg` 的别名）而不是 `/quit`。 |
| **补全会话以「写入的文本区间 + 光标位置」为身份** | 用「当前词」判断是否继续循环，在首次 Tab 扩展公共前缀后就会失配（词变了）；只看区间内容则会在用户接着输入时错误地继续循环。两者都要满足才算同一次补全。 |
| **昵称补全在行首才补 `: `** | 行首补全昵称的目的就是「称呼某人」；句中补全只是插入一个词，加冒号会把句子写坏。 |
| **补全频道参数时无 `#` 也能匹配** | `/join rust` 是所有人打字的方式；匹配时同时比对 `rust` 与 `#rust`，但替换结果一定带 `#`，因为有线格式需要它。 |
| **首字母 Tab 只补到公共前缀，不补冒号** | 公共前缀是片段而不是一个完整的昵称，按昵称规则加 `: ` 会得到 `alic: `。 |
| **`/set` 只能改输入框相关选项，`/help` 只输出到输入框上方** | M2-9 的命令面板才是通用设置入口；这里保持最小，避免两个入口各自演化。 |
| **草稿、历史、最后发言人放在 composer 自己的 store 里** | 它们既不是后端状态也不该被当作会话数据持久化（M3 才落地）。放在 `session` store 里会让人误以为它们和消息同源。 |
| **模式操作只保留一条 IPC 通路 `set_mode`** | `op` / `voice` / `ban` 只差模式字母与参数，具体动作在前端拼装（`setMemberMode` / `banUser`）。每加一个权限动作不必改 Rust。 |
| **`TOPIC` 用 `Option<String>` 区分查询与清除** | `TOPIC #c`（查询）、`TOPIC #c :text`（设置）、`TOPIC #c :`（清除）是三个不同的请求；用 `None`/`Some("")` 保留这个区别，而不是让 `undefined` 兼表其一。 |
| **mock 服务器的观测状态无条件同步** | 原先「非空才同步」的写法让 `PART`、清除 topic、`AWAY` 复位永远传不到观测端——mock 自己藏起了被测行为。测试直接暴露了这个缺陷。 |
| **单字尾参数不带冒号** | `AWAY lunch`、`KICK #c bob spamming` 与 `AWAY :lunch` 在协议上等价，`to_wire` 取最简形式；含空格或空串时才补冒号。断言这类线格式时不要写死冒号。 |
| **可用性验证优先用 jsdom 组件测试** | 本机受限环境无法启动 GUI 截图（沙箱拒绝了提权）。组件测试能覆盖权限判定、禁用态与命令参数，比截图更严谨；纯视觉问题暂时只能靠代码审查。 |
| **快捷键也是一张表** | 派发、命令面板、将来的帮助面板都从 `SHORTCUTS` 读。表里同时决定了按键怎么写（`Ctrl+K` / `⌘K`），避免同一个组合在两处各写一遍字符串。测试还断言「没有两个快捷键占用同一组合」——重复绑定意味着一方永远不会触发。 |
| **修饰键严格匹配** | `Ctrl+Shift+K` 不得同时触发 `Ctrl+K`，否则两个快捷键都变得不可靠。`mod` 按平台解析为 Ctrl 或 Command，其余修饰键必须双向精确相等。 |
| **面板打开时吞掉其它快捷键** | 面板自己处理方向键与回车；此时执行 `Ctrl+W` 会作用于用户看不见的缓冲区。只有「开关面板」这一个快捷键例外。 |
| **指针事件用 `mousedown` 而非 `click`** | 面板输入框失焦会先关掉面板，`click` 就再也到不了。同时 `onMouseDown` 里 `preventDefault` 把焦点留在输入框。 |
| **缓冲区排序抽成 `orderedBuffers`** | 侧栏显示顺序与「下一个/上一个会话」必须一致；各写一份的话，快捷键迟早会跳到不是下一行的位置。 |
| **`digits` 属于快捷键而不是按键组合** | 「跳到第 N 个会话」是一条语义，写成 9 行只会让表和面板都变吵；匹配时由所属快捷键提供该标志，避免两处各写一份而互相矛盾。 |
| **草稿即输入框的值** | 原先输入框另存一份本地 state，导致切换 buffer 时要用 effect 同步，而那个 effect 与任何外部写入（命令面板插入命令）都是竞态。改成直接从 store 派生后，同步逻辑与竞态一起消失。 |
| **面板插入命令而不是执行命令** | 大多数命令需要参数，猜参数比多按一次回车更糟。面板的「操作」立即执行、「命令」写入语法，两种行为各自可预期。插入是非破坏性的：可能正打到一半，丢掉那句话是用户没要求的损失。 |
| **两侧栏的收起按钮长在被收起的栏上** | 收起后留一条 9px 的窄条放展开按钮：只留快捷键的话，不知道快捷键的人就进了死胡同。折叠状态持久化，`sendOnEnter` 与折叠都区分「键不存在」和「存了 false」。 |
| **高亮判定放在 `lib`，不放在 store 或 feature** | session store 要给每条消息打 `highlight`，设置侧要维护规则表；放在任何一侧都会让另一侧跨层引用——而 session store 引用一个 feature，等那个 feature 想要 buffer 时就成环了。 |
| **通知在 `applyMessage` 里发出，不在事件桥里** | 判定所需的全部信息都已经在那个函数里：忽略过滤、回放去重、buffer 是否在前台。在别处再写一份相同规则，就是多一份会写错的规则。 |
| **`mentions` 从 session store 移到 `lib/highlight`** | 昵称提及与关键词高亮是同一个问题的两半，放在一起才能共用边界判定；迁移后原测试随实现一起搬，避免两份实现各自演化。 |
| **关键词边界只认 ASCII 词字符** | IRC 是 ASCII 协议、昵称也不含其它字符；而 CJK 没有空格，若把汉字算作词字符，中文关键词在句中反而匹配不到——恰好与预期相反。 |
| **规则以「折叠后的模式」为身份** | 同一个词添加两次应当更新一条规则，而不是叠两条：`/highlight rust` 打两遍的意思就是一条。因此模型里没有单独的 id 字段。 |
| **高亮提醒是有限栈、可点可关** | 侧栏的未读徽标才是持久记录，所以横幅只显示最近几条、关掉不丢信息。桌面通知、托盘、声音需要三平台各自的权限模型，按既定决策留到 M8。 |
| **窗口标题走 Tauri API，`core:window:default` 不够** | 该默认权限集只含只读命令，`document.title` 也不会同步到 OS 窗口标题，因此必须显式加 `core:window:allow-set-title`。标题报的是「有内容的会话数」而不是消息数：会随每行增长的计数器不再是一个信号。 |

**目视发现并修掉的两个缺陷**（自动化测试都抓不到）

1. **启动瞬间的消息永远不会被高亮或提醒**：`applyMessage` 从 store 的 `networks` 里查自己的昵称，
   而自动连接在前端订阅之后、`listNetworks()` 返回之前就推来了开场消息，此时 `networks` 为空，
   于是这些消息一律判为「不是高亮」；等昵称补上时它们已因 `seq` 去重不会再被处理。
   修法是让后端把它本来就用来计算 `is_self` 的昵称一并带上（`IncomingMessage.self_nick`），
   前端优先采用——界面不该重新推断协议层已经知道的事实。
2. **提醒横幅遮住右侧栏**：原先 `fixed` 在窗口右下角，压住了「核心模块」卡片。
   改为锚定在消息区内，不再遮挡会话树与成员列表。

### 控制字符的显示规则（目视验收后按反馈定的）

控制字符没有字形，浏览器只能画成豆腐块 `▯`，而方块本身什么信息都没有：看不出原本是哪个字节。
规则按「这个字节有没有显示含义」分两类：

| 类别 | 处理 | 理由 |
| --- | --- | --- |
| mIRC 格式码（粗体、斜体、下划线、删除线、等宽、反色、重置、调色板色、十六进制色） | **按格式渲染**——颜色、下划线等如实呈现 | 这是发送方的本意；消息列表与原始流量两个视图行为一致 |
| 其余 C0 控制码与 DEL（CTCP 帧 `\u{0001}`、游离控制字节等） | 消息列表**丢弃**；流量视图显示为 `\xNN` | 它们没有显示含义。流量视图是查「收到了什么」的地方，`\x01VERSION\x01` 比两个方块有用得多 |

原始流量视图同时保留未解析的 `line` 作为 tooltip：渲染后的行无法回答「那是加粗，还是真的有
个 `\u{0002}`」。**刻意不做**：丢弃零宽连接符与变体选择符——它们在 emoji 序列里是正常内容。

解析只由后端做（`ircuit-proto::formatting`），前端不重写一份。`RawTraffic.segments` 仅在该行
确实带格式时才有内容，普通行保持为空，流量环形缓冲区不为用不到的解析付代价。
